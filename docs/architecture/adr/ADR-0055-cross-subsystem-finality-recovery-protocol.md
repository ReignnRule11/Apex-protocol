# ADR-0055 — cross-subsystem finality recovery protocol

- **Status:** Proposed for review; no production adoption.
- **Date:** 2026-11-08
- **Context:** Phases 20G2C5–C7 established fail-closed commit outcomes, an isolated redb finality journal and controlled userspace process-termination tests. They do not coordinate the Malachite consensus WAL, signer reservation journal, finality journal and materialized application state. Treating separate stores as one atomic transaction would be incorrect.
- **Decision:** Define a startup recovery gate and explicit authority model. The signer reservation journal is monotonic and must never be rewound; the consensus WAL is replay evidence but not application-state authority; the finality journal is the ordered APEX application commit ledger after native certificate verification and canonical identity binding; the application database is a rebuildable projection. Startup remains locked until the stores reconcile.
- **Commit ordering:** Reserve exact signing bytes before signing; require engine WAL durability before relying on consensus messages; natively verify and bind finality; atomically append identity/payload/tip to the finality journal; materialize application state idempotently; acknowledge finality only after the journal and projection agree.
- **Recovery:** Replay only authenticated, ordered WAL finality evidence that extends the journal tip. Rebuild an application projection that is behind. Halt on journal-ahead-of-WAL, signer-coordinate mismatch, WAL signature without reservation, conflicting finality, application state ahead/conflicting with journal, missing evidence or untrusted backup rollback.
- **Non-decisions:** No Malachite WAL capability is assumed; no adapter or runtime is implemented; no cross-database atomicity, anti-rollback anchor, power-loss durability or production safety claim is approved.
- **Consequence:** Future integration has an explicit fail-closed contract and test matrix. If the pinned engine cannot expose sufficient authenticated WAL/replay evidence, the integration must be redesigned rather than bypassing the recovery gate. G2/G4 remain BLOCKED; release remains NO-GO.
